## 四区域主页与资源分配方向（2026 年 10 月 8 日）

用户提出把主页发展成四个有不同名字的游戏区域，每区暂按四百题规划。各区承载轻松、标准、挑战与专家体验，具体玩法继续考虑；专家内部的四组各一百题可以组成专家区的四百题，不另外重复计数。候选名称、题库制作要求与待定规则见[四区域与提示资源讨论](gameplay-ideas.md#四个游戏区域题库规模与提示资源讨论方向)。

用户判断正常尺寸手机可优先尝试三排六瓶的十八瓶布局，二十四瓶略有压力。颜色数、每色总量与空瓶数暂不确定；先验证十八瓶的大瓶尺寸、可读性、触摸区和倒水运动，再考虑二十四瓶。当前已实现的十二瓶、两排布局仍是安装基线。

Easy 区提示额度较多，专家区极少或几乎没有提示，题目难度和辅助资源共同参与体验设计。提示额度、发放方式、跨区余额与 Premium 无限提示的兼容方式尚待明确。撤销和重来保持自由恢复方向；不据此增加生命、等待恢复或付费救援。

以上是后续产品方向，未改变 v5 千关主线、现行提示规则或存档。本文后面的早期第一期候选和阶段描述不直接作为四区域的实施配方。

## 第一期候选范围

第一期把已验证的演示发展成可以独立游玩的单人纯玩版本。20 个经典关卡和 5 个颜色解锁关可作为教学与主线的候选内容，不是整个游戏的内容上限，也不是已生成或已验证的关卡库。通用求解器、生成器和自由游玩用于持续提供内容；是否加入每日题以及机关进入哪一期，按系统方案审阅后确定。

| 功能 | 第一期建议 | 边界 |
|---|---|---|
| 经典分拣 | 做 | 每瓶四层，空瓶或顶部同色接收，连续同色按余量转移 |
| 原创美术与倒水 | 保留并完善 | 沿用已经验证的玻璃瓶与液流方向，不复制竞品角色和特效 |
| 选中与非法操作反馈 | 做 | 瓶子抬起、再次点击取消、换来源；无效目标不改变局面 |
| 撤销与重开 | 做 | 不消耗金币或限量道具；可以从卡住的局面返回 |
| 无合法移动提示 | 做 | 提示撤销或重开，保留当前局面；不扣生命、不强制结束 |
| 完成反馈与下一关 | 做 | 每个非空瓶装满且单色；明确完成并可继续下一关 |
| 轻量主页与关卡选择 | 做 | 继续游玩、关卡入口、设置；不套用竞品五菜单框架 |
| 本地进度 | 做 | 保存当前关卡、棋盘与已完成记录；不引入账号或云同步 |
| 关卡制作与验证 | 做 | 人工教学关与程序候选共用模型，独立求解和筛选后进入内容池 |
| 通用内容工具与自由游玩 | 系统方案候选 | 生成、求解、编码与筛选先打通，随后接无限次数的休闲抽题 |
| 手机和平板适配 | 做 | 检查小屏、瓶数增加后的布局和低端 Android 表现 |
| 基础设置 | 做 | 玩法说明与减少动态效果；音效和震动先单独讨论 |
| 完成指定颜色解锁容器 | 第一期之后的首个候选 | 用少量实验关验证；是否提前纳入第一期需本轮讨论 |

完整体验候选流程为“继续游戏或选关 → 分拣 → 卡住时撤销或重开 → 完成反馈 → 下一关”。第一次进入用可以动手完成的短教学关；介绍集中在当前操作，不要求阅读一整页规则。

本地进度只记录已经接受的游戏操作，动画不决定真实液体状态。退出前台、重新打开、关卡完成及重开都应有明确恢复结果。撤销历史可以限定在本次打开关卡的会话，是否跨重启保存仍待讨论。

### 暂不进入第一期的功能

| 功能 | 安排 | 原因 |
|---|---|---|
| 金币购买、礼包、付费救援、第三方广告、Premium | 不采用当前产品方向 | 与此前免费和无第三方广告方向不一致；不是默认延后上线 |
| 生命限制、限量撤销、解题倒计时 | 第一期不采用 | 先建立自由思考和可恢复操作的体验 |
| Shuffle 与额外瓶子道具 | 后续评估 | 先区分关卡本身的空间设计与辅助效果，避免依赖道具才可解 |
| 每日题 | 系统方案候选 | 与自由游玩并列，需先有已验证内容、日期映射、完成记录和明确重试规则 |
| 隐藏颜色、钥匙、固定瓶、变容量 | 分别验证 | 每次引入一种机制，规则与求解器要共同支持 |
| 周赛、倍率活动、排行榜、金币经济 | 后续选择性讨论 | 需要明确对解谜体验的价值，不因竞品已有就全部加入 |
| 收藏、卡包、角色和主题章节 | 后续候选 | 需要持续美术内容、获取和完成目标 |
| 好友协助、团队、共享棋盘、账号 | 保留长期方向 | 先定义合作价值和单人可游玩的边界，再引入联网 |
| 推荐时间额度与服务端结算 | 后续候选 | 与解题倒计时是不同系统，不能在第一期混用 |
| 音效与震动 | 后续讨论 | 先完成视觉与操作闭环，再确定反馈强度和开关 |

### 第一期验收条件

第一期内容需要玩家在不联网时能开始、继续、撤销、重开和完成关卡；一次正常操作、快速连续点击、切后台和重新打开都不能造成液体数量变化或错误进度。关卡应有可复现的解法，失误造成的死局允许恢复，不依靠付费或道具。

新增多色、多瓶和保存行为后，按[设备测试说明](device-testing.md)在小屏 iPhone、低端安卓和平板继续试玩。已有演示的真机认可不直接覆盖尚未实现的内容。

## 关卡设计方法

### 从一个概念到多个组合

关卡不能只靠增加瓶数和颜色数变难。每一组先教一个操作概念，再要求玩家计划几步、保留中转空间，最后组合已学规则。以下分组是第一期 20 关的候选内容配比，不是完成的关卡数据：

| 关卡组 | 颜色与瓶子候选 | 要玩家理解的事情 |
|---|---|---|
| 1 至 3 | 两色，四瓶，四层容量 | 点击来源与目标，利用空瓶，连续同色一起倒 |
| 4 至 7 | 三色，五瓶 | 有序合并顶部颜色，给下一步留下空间 |
| 8 至 12 | 四色，六瓶 | 比较不同来源，避免过早占满中转瓶 |
| 13 至 16 | 四至五色，六至七瓶 | 利用部分接收，先搬走一段以露出需要的颜色 |
| 17 至 20 | 五色为主，七瓶 | 组合多个熟悉操作，形成需要提前规划的收尾局 |

每组内部安排轻松关与思考关，不承诺关卡号越大就必定更难。颜色数量与瓶数只控制规模，最终难度由验证和试玩共同判断。统一使用轻松、标准、思考、挑战四档，另由编排器控制难关与放松关的顺序；每日题一周两次较难的候选安排见[系统方案](system-design.md)。

### 制作与验证流程

1. 先写清这一关教什么、关键决策是什么，再确定颜色、容量和瓶子数量。
2. 经典关卡保持每种颜色总量等于一个完整瓶容量；检查数量、容量和初始状态合法。
3. 人工编排或产生候选局面，再用与游戏相同的合法操作求解。不能假设从完成态随意打乱或做几次操作就一定得到合适的可解谜题。
4. 保存一条可回放的参考解法，检查每一步合法以及最终达到完成条件。求解被中断或超过限制时标记为尚未验证，不将其写成无解或加入发布库。
5. 记录解法长度、分支选择、中转空间压力和试玩难点。最短步数并不能独立表示玩家体感难度。
6. 在界面实际试玩，检查识色、误触、反馈和是否需要猜规则；淘汰只有重复搬运、几乎没有决策的局面。
7. 打散相似关卡顺序；只交换颜色或瓶子位置的同构局面不作为大量新内容。

第一期求解器需要支持多种颜色和多瓶，当前代码中的小规模 solveDemo 只用于两色演示，不能直接当作完整内容生产工具。后续每一种特殊机制都应扩展真实状态、合法操作和求解验证，再制作对应关卡。

隐藏颜色的关卡要区分“知道真实颜色时可解”与“玩家按逐层揭示的信息能够合理推进”；不能只做前一种检查就认为公平。必要的中转空间、钥匙和解锁瓶子必须计入验证，不把动画完成当作触发规则的来源。

### 三个原创关卡构想

下面只有玩法目标和候选规则，没有生成或发布未经验证的液体排列。

| 构想 | 候选规则 | 关键决策与原创表现 |
|---|---|---|
| 色彩唤醒 | 完成指定颜色的单色满瓶后释放一个备用容器 | 先完成哪种颜色会影响空间；用玻璃底环亮起、柔光显现表现解锁，避免复刻布罩或碎箱 |
| 回流工作台 | 带原创固定底座的容器只接收，限制容量并明确标识 | 留出容量给正确颜色；“只接收”是我们的候选规则，不是竞品已确认规则，需证明能完成且不会误导 |
| 逐层透光 | 液体层被半透明雾遮挡，到顶部时显色 | 根据已知颜色安排空间；先教学再组合，不同时加入钥匙和固定瓶 |

钥匙也可变成独立机制，例如将带标记的液体移到指定接收瓶后打开侧边容器，但触发条件要明确并允许完整撤销。不同容量要解释分层单位，不能让玩家靠瓶高猜容量。

“一关只能靠一次随机洗牌救活”不作为正常设计目标。若以后提供洗牌，要保持每种颜色数量不变，明确只作用一个瓶子还是全局，并验证钥匙、遮挡与已完成状态的处理。

## 下一轮产品讨论

纯玩原则已经确定。下一轮先审阅[系统方案](system-design.md)中的模型、内容工具与持续游玩顺序，再讨论下列产品边界：

1. 教学与主线的 20 个经典关是否保持该规模，何时加入自由游玩与每日题？
2. 第一种新机制优先选“完成颜色解锁容器”，还是先只做经典关卡，把所有机关放到下一期？
3. 合作章节继续作为后续方向，是否始终允许玩家同时继续单人主线，避免等待好友时无法游玩？

竞品未知项继续在独立记录中维护。具体瓶子排列、难度与奖励数值在功能边界确认后验证，本文不直接成为开发任务或发布承诺。

## 产品方向

用户希望做一款品质认真、玩家无需付费、没有第三方广告和 Premium 的解谜游戏。游戏本身应当好玩，同时给玩家邀请朋友参与的理由，形成持续传播。

Bottle Harmony 还承担整个解谜游戏系列的免费入口，后续通过可选推荐，把感兴趣的玩家带到数独、推箱子等自有收费游戏，降低整个系列对付费广告的依赖。

长期愿望是在几年内争取百万至两百万用户或活跃用户。累计用户、月活跃玩家和日活跃玩家的最终目标口径尚未确定；此前服务器与增长核算使用月活跃玩家作为假设，不能把这些计算当成规模承诺。

## 经典倒水玩法基础

初步玩法基础为每瓶容量四层，关卡可以超过四种颜色。玩家先选择源瓶，再选择目标瓶；空瓶可以接收任何颜色，非空瓶只能接收与顶部相同的颜色。每次倒出顶部连续同色液体，直到这一段倒完或目标瓶装满。

所有非空瓶都装满且只有一种颜色时通关。支持撤销和重开；玩法不设置解题倒计时。推荐额度限制的是可游玩时间，与解题速度竞赛分开设计。

颜色数加两个空瓶是候选初始配置，尚需关卡验证。关卡应当可解，难度与必要合作都需要验证。

## 五小关组成合作章节

这是用户提出、希望继续丰富的当前重点：一个大关由五个小关组成，主玩家完成三个，另外两个需要好友协助。没有完成好友任务，就不能通过这个合作大关。

| 小关 | 示例分工 |
|---|---|
| 第一小关 | 主玩家完成 |
| 第二小关 | 主玩家完成 |
| 第三小关 | 好友协助完成 |
| 第四小关 | 主玩家完成 |
| 第五小关 | 好友协助完成 |

表格只表示分工示例，不要求严格按这个顺序游玩。三个个人任务加两个好友任务是本次讨论中的候选组合，并非所有章节都已经确定采用同样数量。

### 提前展示任务并直接邀请

进入章节时就展示哪些是自己的任务、哪些是好友任务，让玩家从开始便能邀请协助。分享应当直接指向这个章节中需要帮助的小关，朋友进入后知道正在帮助谁、要完成什么。

好友小关可以先沿用普通单人倒水关卡。每个人独立完成自己负责的小关，完成结果计入共同章节，不需要一开始就共享瓶子状态。

### 异步完成并保留共同进度

用户希望朋友不必当天完成，两天后再来帮助也可以。主玩家先完成自己的任务，朋友稍后完成协助任务；五个任务全部完成后，章节通关。

用户希望主玩家通关时，协助朋友也能共同过关。具体记入哪种进度仍待确定。助手建议给予参与者共同章节的通关记录，同时保留各自单人进度；不因为帮助了一个较后面的章节，就自动跳过朋友中间所有单人关卡。

### 当前候选体验安排

以下是助手建议，尚未最终确认：

- 允许同一位好友完成两个协助任务，也允许两位好友各完成一个。
- 主玩家可以先完成三个个人任务，避免等待好友才能开始。
- 已有好友可以反复合作，不要求每个章节都邀请新人。
- 未完成的协助任务允许重新邀请其他朋友接力；保留已经完成的任务。
- 等待协助期间仍可游玩单人关卡。合作章节是否与单人主线分开，需要用户决定。

好友任务应当是一道有完整解题乐趣的题目，而不是只点击一次即可完成的占位任务。初期可以短一些、难度适中，让朋友能感到自己确实帮上了忙。

## 后续增加共同解题

用户希望后面的章节逐渐变成需要配合的合作关。候选推进方式是从独立任务分工开始，再加入队友之间的帮助，最后加入共享棋盘。

### 共享棋盘与瓶子分工

双方看到同一个棋盘，每个人只能从自己负责的瓶子倒水，可以倒入任何符合规则的目标瓶。关卡应当设计成双方都必须进行有效操作才能完成。

候选教学局有两种颜色、四个瓶子。以下液体顺序均为从下到上：

| 瓶子 | 初始液体 | 操作者 |
|---|---|---|
| 一 | 红 蓝 红 蓝 | 玩家甲 |
| 二 | 蓝 红 蓝 红 | 玩家乙 |
| 三 | 空 | 玩家甲 |
| 四 | 空 | 玩家乙 |

双方通过移动自己负责的瓶子，最终将红色集中到第四瓶、蓝色集中到第三瓶。该示例说明瓶子分工的合作方式，尚未纳入实现或关卡库。

候选交互是不强制轮流，支持在瓶子上标记移动建议，需要队友自己执行。共享进度保留，支持同时游玩或稍后接力。第一版可以用瓶子标记交流，不必引入聊天系统。

### 其他远期候选玩法

- 分区交换：各自有一个棋盘，通过公共瓶子交换颜色。
- 信息协作：各自掌握部分颜色信息，通过提示共同规划。
- 小关之间提供帮助：一个任务完成后，为队友提供空瓶或提示；关卡必须按这些帮助验证。

这些玩法只是后续讨论候选，不属于当前已批准的实现范围。

## 推荐与游戏时间的候选规则

用户的体验目标是有三至四位持续活跃的直接推荐朋友，就能获得比较充足的游戏时间。推荐人数不限制为三或四人。

目前讨论的候选数值是前七天自由玩，第八天起每天获得三十分钟基础时间；直接推荐的朋友实际玩一分钟，推荐者获得一分钟。朋友的时间不会因为产生奖励而扣减，自己的前七天也可以积累推荐奖励。

推荐关系可以继续延伸，但助手建议只计算直接推荐奖励。例如甲推荐乙、乙推荐丙，乙游玩给甲奖励，丙游玩给乙奖励；甲不直接领取丙的游玩奖励。每人只绑定一个推荐者、关系不能循环，是候选约束。

用户希望看到朋友带来的游戏时间。展示粒度和告知方式待确定，助手建议展示有效时长贡献，不公开具体上线时刻和操作记录。

### 最近七天补领

用户提出可以限制为登录时只补领最近七天的奖励，更早未领取的部分不再补发。助手建议区分未领取奖励与已经领取的余额：前者七天内可领取，后者继续保留。

这一规则尚未最终确定。每日基础时间是否跨日保留、奖励余额是否长期保留、七天如何划定日期边界，也需要一起明确。

### 核算示例

按每日三十分钟基础时间、直接推荐奖励一比一计算，三位朋友每天各玩三十分钟，推荐者当天新增可用时间共两小时；四位朋友则是两小时三十分钟。这是条件成立时的算术示例，不保证邀请成功后朋友会持续活跃。

合作游戏只计算每个人自己的有效游玩时长，不把房间总时长重复记入每位参与者。

## 服务端记录与成本讨论

用户提出开始游戏上报、每五分钟上报、退出时再上报；保存当前汇总、最近七天记录和必要结算记录，按用户每天汇总一条数据。

助手建议上报累计有效游玩时长，并只结算尚未处理的增量；开始到退出的墙上时间不能直接当作游玩时间。暂停、后台与断网处理，以及强制关闭后是否允许补报，需要进一步决定。

每天一条汇总记录可以减少长期数据行数，但每次上报仍会更新该记录。领取奖励与增加余额应当一起完成，重复请求不得重复发放。若保留完整原始上报七天，还会有独立的明细数据，不能将其算作只有每日汇总。

时长结算可以每五分钟处理；共享棋盘的倒水操作则需要及时同步。

此前以百万月活、十万日活、每人每天三十分钟估算，五分钟周期上报约每天六十万次，开始和结束事件另计。该用户规模与使用习惯是假设，不是实际流量。

2026 年 10 月 5 日讨论记录中的估算是 AWS Lightsail 后端二十四美元加标准托管数据库三十美元，基础套餐合计五十四美元每月；自建 PostgreSQL 也可考虑两台二十四美元服务器，另计备份。该估算未在本次竞品整理中重新核查。价格不代表性能保证，税费、流量超额、额外备份及人工维护另外考虑。

## 自有游戏推广入口

用户希望通过这款游戏推广自有收费解谜游戏。候选方式是在主菜单设置更多解谜游戏入口，由玩家主动查看和进入商店，不干扰正常游玩。

Google Play 官方说明：仅通过主菜单 More Apps 一类入口交叉推广，且不干扰或混淆游戏功能时，可以申报不含广告。横幅、插屏或广告墙形式的自有应用推广，则需要申报含广告。

这一许可针对交叉推广形式，不代表本文的时间奖励或邀请机制已经获得商店审核认可。

## 后续合作与时间额度问题

优先继续明确以下问题，之后再划定具体功能实现范围：

1. 合作章节与单人主线分开，还是某些主线大关必须好友协助？
2. 两个好友任务可否由同一位朋友完成，还是要求两位不同的朋友协助？
3. 共同过关对朋友意味着共同章节记录、个人进度推进，还是两者兼有？
4. 好友长期不完成时，怎样重新邀请或接力？等待期间哪些内容仍可玩？
5. 哪些章节开始引入真正的共享棋盘？每章任务数是否始终为五个？
6. 基础时间、奖励领取期限、已领取余额与跨日边界分别怎样确定？

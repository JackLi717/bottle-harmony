# SQLite 关卡库与游玩统计方案

更新日期：2026 年 10 月 8 日。状态：SQLite 关卡库、玩家库及本地统计开发完成，165 项自动回归、类型／代码检查、Expo Doctor 21 项及全部题目读回验收通过；平台检查和真机待验项见[设备验收](device-support.md)，联网上传尚未实施。用户确认第一版正在申请上线，尚未进入测试，没有玩家。本次直接建立新数据库基线，不导入或兼容旧 JSON／AsyncStorage 数据；新版首次启动重新开始，其后恢复自己的 SQLite 数据。已提交的 0.1.1（5）包仍是此前版本，源码改造不代表已更新商店包。

目标是建立统一的 SQLite 数据层，在本机保留足够准确的游玩经历，为将来的难度校准、个人记录、辅助政策和联网分析提供依据。近期可以不展示统计界面。恢复存档、统计分析和未来云存档分别设计；存储改造不改变当前关卡布局、提示、奖励或通关规则，也不代表批准尚待讨论的新玩法。

## 保存内容

| 数据层 | 保存内容 | 保存原则 |
| --- | --- | --- |
| 恢复存档 | 当前进度、主线／副关／重玩局面、撤销历史、提示资源与辅助状态 | 优先保护，逻辑状态先提交，表现不授予进度 |
| 长期摘要 | 每关及总体的时间、次数、首次完成、辅助使用和记录完整性 | 长期保留；按内容与指标版本区分 |
| 详细记录 | 按序发生的倒水、撤销、重来、提示、暂停、恢复和完成 | 有期限且有容量上限；过期前已形成摘要 |

当前撤销历史只描述仍保留的路线，撤销会移除步骤，重来会清空路线。它不能代替实际操作日志，也不能反推出历史尝试、用时和提示来源。详细记录只保存必要字段，不逐步复制整个棋盘；需要回放时使用对应题目、规则版本和动作序列，包含融化及备用瓶启用。

## 挑战与尝试口径

一次首次通关挑战可以包含多次尝试；一次尝试可以跨多次应用游玩。分别使用 `challengeId`、`attemptId` 和 `playSessionId`。

- 首次实际进入未完成题目时开始挑战和首次尝试；后台预建下一题不算开始。
- 返回主页、切后台或关闭后恢复，同一局面继续原尝试。暂停不算失败或放弃。
- 有效重来结束原尝试，开始新尝试；先前用时、倒水和辅助仍计入首次通关前累计。
- 撤销不开始新尝试，实际发生的倒水和撤销计数不倒退。无效果的操作请求不计为成功操作。
- 首次逻辑完成结束首次通关挑战；撤销最后一步、重来再完成不会重复计入首次完成、奖励或推荐资格。其后操作另标记为完成后游玩，避免污染首次通关指标。
- 主线、副关、重玩分别记录；每次明确开始重玩建立独立挑战，恢复重玩沿用原记录。内部试玩排除在正式分析之外。

例如，第 35 关第一天玩 3 分钟，第二天继续并重来一次，再玩 2 分钟完成：一次首次通关挑战、两次尝试、跨两次游玩，累计前台时间约 5 分钟。

新版从新进度和新的统计观察起点开始，不读取旧存档。异常中断、写入缺口或日志截断的记录标记 `partial`；缺失时间与次数为未知，不能填零，也不能声称完整观察了首次尝试。

## 指标目录

| 方向 | 原始计数或事实 | 后续用途 |
| --- | --- | --- |
| 进度 | 正式主线／副关首次完成、当前关、首次完成时间、里程碑 | 推进速度与阶段分布 |
| 游玩习惯 | 游玩日期、前台游玩片段、每次完成数、返回间隔 | 游玩长度与回访 |
| 每关投入 | 首次通关前累计时长、尝试数、跨游玩次数、未完成状态 | 实际受阻程度 |
| 操作量 | 手动与提示倒水数、成功撤销数、重来数、最终路线步数 | 探索成本与操作负担 |
| 提示需求 | 请求、成功执行、首次使用的动作位置、当时资源与权益来源 | 辅助需求与时机 |
| 搜索结果 | 找到路线、证明无解、预算未知、取消、执行未成功及搜索耗时 | 提示可用性；与已扣券行为分开 |
| 提示资源 | 计划奖励、实际入账、达到上限未入账、消耗、余额为零时请求 | 区分题目困难与辅助短缺 |
| 卡住与恢复 | 无合法移动的进入次数、按需搜索证明无解、后续撤销／重来／融化／继续 | 恢复手段的作用 |
| 题目辅助 | 副关融化、备用瓶启用及发生位置、完成时辅助状态 | 机制与辅助使用 |
| 重玩与偏好 | 重玩题目和次数、容器使用时长、声音与符号偏好变化 | 内容偏好与可用性 |
| 运行质量 | 保存／恢复失败类别、提示性能；按需抽样的渲染性能 | 区分技术阻碍与解题困难 |

同一次提示要关联请求、搜索结果和最终执行，不能把找到了路线当成成功执行或扣券。提示执行的倒水属于总倒水数，并有来源标记。以首次完成前全部尝试是否执行过提示判断无提示首次通关；融化、备用瓶等辅助独立标记。

卡住按进入一个连续状态的次数统计，不按重绘次数累计。无合法移动、证明无解、搜索预算未知分别记录。沿用已有规则检查与主动提示搜索，不为统计增加每步完整求解。

## 时间口径

分别记录棋盘可见且应用前台的总时长、操作受限时长，以及二者之差的可操作等待时长。受限区间包括实际阻止操作的动画、搜索及覆盖界面，重叠区间取并集，不重复扣除。完成后的礼花和继续等待不计入解题时长。

目前倒水动画约 1.9 秒，不能把总时长直接当成思考时间。长时间无输入可能是思考，也可能是离开手机，保留长停顿信息或分布，不直接推断原因；阈值随指标版本记录。

持续时间使用单调时钟，在前后台和页面切换处分段累计；日期用于里程碑和日汇总，记录时区口径。跨进程间隔不补成游玩时间。异常终止只保留已落盘片段，标记中断或不完整，不推算退出后的时长。

## 标识与一致性

每条记录带应用版本、统计格式和口径版本、题库版本、稳定关卡 ID、模式／区域标识、规则版本、辅助政策版本、当时权益、挑战和尝试 ID、动作序号、修订号及完整性状态。当前模式区分主线、副关、重玩及已批准的五题记忆原型；记忆规则与独立时间口径见[记忆专题](memory-mode-plan.md)。预留字段不等于批准其他玩法。

安装记录使用随机 ID，推荐参与记录使用独立 ID；重装可以建立新记录，不跨重装追踪、不指纹识别、不去重自然人。活跃与推荐结果分别表述为安装记录数或参与记录数。

计数以逻辑接受的动作和明确的页面／生命周期边界为依据，不能由动画结束或组件挂载触发。使用唯一动作编号防止重复处理。派生摘要记录最后处理序号；日志清理后保留摘要及必要的去重边界，不能因删除日志重新累计。

目标数据库内，进度快照、动作事实和相关摘要通过事务形成一致的已持久化修订。视觉可以先响应已接受的内存动作，但未提交到存储的动作仍可能因强制退出而丢失。统计失败不应阻止玩家继续，必要时优先保住可恢复进度并明确标记统计缺口。数据库事务不包含动画、网络请求或长时间搜索。

## 新版统一 SQLite 存储

新版运行时的唯一持久化技术为 SQLite。关卡、参考解法、评级与特征、玩家进度、棋盘与撤销、统计、声音／符号／容器等本地偏好全部进入数据库，不保留 AsyncStorage 业务数据或运行时 JSON 题库作为并行来源。图片、音频等媒体继续使用资源文件。

同一种 SQLite 技术分为两个职责独立的数据库：`content.sqlite` 是随包分发的关卡库，运行时按只读内容使用；`player.sqlite` 是应用私有目录中的可写玩家库。更新关卡库不替换玩家库，玩家事务不修改正式关卡。跨库关卡引用通过题库版本和稳定 ID 校验，不假定跨库外键或两个数据库之间自动具有单库事务保证。

应用按需查询题目、解法和诊断，不在启动时读取全库并转成巨大 JavaScript 对象。当前核心仍使用独立的 TypeScript 规则和会话模型，数据库适配器在进入关卡时构造并校验需要的模型；规则、求解和动画不依赖 SQL。

旧 JSON codec 只留作离线回归，不接入运行保存，不建立兼容层。新数据层按有关联的记录增量写入，不把旧的整份存档字符串原封不动搬进单行，也不在每一步重建、编码和回放全部历史。保留恢复校验与撤销能力，并为数据库中的会话历史设置独立预算。

现行精简题库解码器要求恰好 1000 题。新库用内容包、模式、稳定关卡 ID 和关卡顺序建模，题目数量由内容清单描述；当前内容清单仍严格验收 1000 主线和 50 副关。未来扩容需要对应规则和生产校验，不因表结构可扩展就自动开放新玩法。

## 关卡数据库与生产验证

正式运行与分发的关卡库改为 SQLite，包含当前千关主线、50 道副关及相应证据。既有离线 JSON 可以保留为制作输入和校验中间材料，应用不再把它们作为运行时关卡源；这不要求重新生成或改变已验证题目。

| 内容表组 | 内容 |
| --- | --- |
| 内容清单与顺序 | 内容版本、规则版本、模式、关号、主副关绑定、配方角色与数量 |
| 关卡与初始布局 | 稳定关卡／瓶子／颜色 ID、四层容量、瓶位、由底到顶的液层、凝固目标与可选备用瓶配置 |
| 参考解法 | 有序的源瓶、目标瓶、颜色与液量；副关冻结和融化解法分别保存 |
| 评级与特征 | D1–D4、人类代理分、模型版本、规划证据、特征标签及完整诊断证据 |
| 生成来源与验证 | 算法、seed、候选序号、参数、结构键、验证版本与内容哈希 |

已实现的内容表为 `metadata`、`levels`、`colors`、`bottles`、`layers`、`solution_steps`、`tags`、`evidence`、`internal_assets`，记忆遮色另用 `memory_masks`。顺序、评级摘要与主副关绑定保存在 `levels` 的可查询列中；完整来源与诊断证据按关存入 SQLite 文本列，按需读取，不作为外部 JSON 题库加载。瓶子及液层保存明确序号，解法保存分支与步骤序号；唯一约束和引用检查防止重号、漏层或引用错题。

构建流程为：既有生产验证通过 → 写入临时 SQLite 内容库 → 从 SQLite 重新读出全部记录 → 用原规则重构与回放并逐项对比 → 检查约束、数据库完整性、外键、全局结构去重和内容清单 → 发布绑定哈希的数据库资源。完整来源与评级证据不得因更换格式丢失，未知搜索结果不能入库。读取新库后的校验必须覆盖副关双状态、备用瓶配置和全部路线，不能只验证导出前的 JSON。

打包时完成数据库事务和日志收尾，分发产物不依赖未打包的 WAL／SHM 文件。库内记录 schema、内容和验证版本；手机只读经过离线验证的内容，不重算完整策略评级。后续新内容以新版本资源验收并切换，不能覆盖正在使用的题目引用。

## 玩家数据库与事务

| 玩家表组 | 内容 |
| --- | --- |
| 进度 | 主线与副关首次完成、当前位置、提示资源及必要里程碑 |
| 会话与撤销 | 主线／副关／重玩各自棋盘、液层、有效动作栈、凝固／融化与备用瓶状态 |
| 挑战与统计 | 游玩片段、挑战、尝试、逐步事实、每关与每日摘要 |
| 本地偏好 | 声音、辅助符号、容器等显式保存项；语言继续跟随系统 |
| 元数据 | schema 和指标版本、安装记录 ID、最后处理序号与完整性状态 |
| 未来在线业务 | 功能实施时再增加上传队列、推荐参与／结算、购买与权益记录 |

已实现玩家表为 `progress`、`completions`、`sessions`、`session_layers`、`play_sessions`、`challenges`、`attempts`、`events`、`level_stats`、`daily_stats`、`hint_requests`、`preferences` 和 `metadata`；五题记忆原型另有独立会话／单位／知识／尝试表，详见[记忆专题](memory-mode-plan.md)。每次接受倒水只追加新撤销快照并替换当前棋盘；每个会话最多保留最近 4096 步撤销，超过后保留校验过的锚点及累计路线偏移，继续正常保存。重来仍回到原题，统计累计不因撤销裁剪而减少。常用查询字段使用列及必要索引，不采用单个全量 JSON 存档值。

一次有效动作在玩家库事务内提交恢复状态、撤销变化、动作事实和相关计数；首次完成及提示资源变化同事务处理，防止一边成功另一边遗漏。重来结束原尝试并建立新尝试，撤销只改变当前路线，不删除已发生的统计事实。无效果请求不产生成功动作，重复事件依靠唯一键去重。[SQLite 事务说明](https://www.sqlite.org/transactional.html)阐明了同一事务全部完成或全部不完成的保证。

小批次异步写入串行调度，后台前刷新已接受动作；累计时长按片段和检查点写入，不每帧写数据库。参数使用绑定，SQL 不由用户输入拼接。频繁操作、长撤销历史和统计查询分别测量，必要时优化索引及批次，不用数据库事务包住求解或视觉过程。

已通过 `npx expo install expo-sqlite` 安装 SDK 57 兼容的 `expo-sqlite ~57.0.4` 并移除 AsyncStorage 依赖。[Expo SDK 57 文档](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/)提供持久化和事务接口，也注明 Web 支持仍为 alpha，需要 WASM 和站点响应头配置；Apple TV 数据库位于缓存目录。全平台目标仍为 SQLite，浏览器 WASM 持久化、TV 缓存清理和内容资源部署分别验证；遇到平台限制须明确解决或支持边界，不能静默回退到旧 JSON／AsyncStorage 方案。

## 容量与保留

长期保留每关摘要和必要里程碑；详细尝试、逐步事件和技术诊断采用时间与容量双上限。可先以最近 30 天、最多 5 万条逐步事件作为测量起点，达到任一上限即清理最早可清理记录；当前作为可调整的工程保留预算，每 100 条动作检查一次，原始事件可短暂超过上限至多 99 条。开放挑战不清理，已结束片段、提示与尝试也有容量上限。实际字节、索引、数据库日志文件及清理后空间也纳入测量。

正在恢复的棋盘和撤销历史由会话快照独立保证，不依赖无限保留统计日志。清理详细记录后，标记不可完整回放，摘要不倒退。上传队列也应有保留策略；尚未联网不能成为无限积累原始数据的理由。

## 新基线初始化

用户确认当前没有玩家，允许直接以新版本重新开始。本次不实现旧存档读取、转换、导入、兼容映射、双写、旧库回退或历史档案；旧开发安装中的进度、提示资源和偏好均不继承。应用不会删除旧开发文件，也不会读取它们；首次新库初始化是唯一的新起点，之后不能以错误为由重建进度。

1. 完成 SQLite 内容库导出与验收，打包当前正式关卡及所有必要证据。
2. 首次启动准备已验证内容库，在一个玩家库事务中创建 schema、初始进度、默认偏好、新安装 ID、统计版本和初始化完成标记。
3. 初始化数据与完成标记一起提交；启动中断重试不得重复建初始记录或发放资源。后续启动读取已有的新 SQLite 数据，不反复重置。
4. 数据库损坏、空间不足、内容版本不符时明确报告并保留可诊断数据，不伪装成首次启动，也不读取旧存档救场。
5. 未来真正开始玩家测试或发布后，再为届时的新 SQLite 基线设计升级兼容；本次重新开始的授权只适用于当前尚无玩家的改造。

当前已有的开发验证、内容来源和构建证据继续保留；不迁移玩家存档不等于删除已验证题目或抹去发布申请记录。

## 联网分析边界

先积累本地数据；联网分析接入时再明确上传字段、历史范围、开关、删除、队列期限和公开说明。默认优先上传必要摘要和有选择的诊断，不因有联网能力自动上传过去全部逐步历史。上传使用记录 ID、修订和服务端去重；客户端断网、超时或未收到确认时可安全重试。

数据解释需要固定分母和观察窗口：关卡完成率以实际进入的首次通关挑战为基础，暂停／尚未完成保持独立；回访指标只纳入已具备完整观察窗口的安装记录，退出和卸载本身不可由缺少后续事件直接证明。只看已完成者会低估受阻程度，通关时间同时观察中位数、较慢群体和未完成情况。辅助不同、内容不同和观察不完整的样本分别分析；较后关卡还存在玩家筛选影响，相关性不直接证明关卡导致流失。

推荐参与、自邀、重装和 Premium 沿用[已确认规则](gameplay-ideas.md#后续商业规则无广告推荐与-premium)。结算凭据与购买验证独立于可裁剪的统计记录，同一参与记录只结算一次。联网统计不等于云存档，也不承诺跨设备恢复。

## 实施顺序与验收

源码入口为 `src/storage/`：内容／玩家 schema、按需关卡查询、增量会话写入、串行事务与修订去重、挑战／尝试／摘要、单调时钟及有界事件。`App.tsx` 在数据库准备完毕后开放界面；失败时显示重试并保留数据库。`npm run content:build` 导出及读回验收关卡库，`npm run test:storage` 运行真实 SQLite 故障与全关卡验收，`npm test` 运行全部回归。生成日志、性能测量和构建证据集中在忽略的 `builds/sqlite-acceptance/`，不复制成文档档案。

浏览器配置 SQLite／WASM 资源与隔离响应头，导出附带 `public/_headers`；本地使用 `npm run web:serve -- <导出目录> <端口>`。SDK 57.0.4 Web 同步桥存在返回长度单字节截断及按迭代次数超时问题，`scripts/patch-sqlite-web.cjs` 在安装后应用最小修正；升级 SDK 时必须重新审核。启动清单异步读取，长历史分页恢复，避免超过同步桥缓冲上限。后续网络、推荐结算和购买仍未接入。

验收覆盖数据库导出后全部题目的一致性与完整路线、按需加载、有效动作计数、撤销和重来后不丢累计、首次完成不重复、跨后台和重启的尝试连续性、提示请求到执行关联、冻结／融化及备用瓶状态、所有偏好持久化、初始化中断与重复启动、事务失败、日志裁剪、重玩及内部试玩隔离。确认应用运行时不再读取旧 JSON 题库或 AsyncStorage，旧开发安装在新版首次启动得到新进度，之后重启正常恢复新库。

低端 Android 和 iPhone Release 真机测启动恢复、写入延迟、队列堆积、持续操作帧率与内存，使用长操作历史和预装多日统计数据。浏览器和 TV 分别验收 SQLite 持久性及内容资源加载；桌面结果不能代替设备证据。上线材料同步说明本地统计实际保存项，联网与内购仍按各自实施状态申报。

# Repository Guidelines

## Scope

Bottle Harmony is a new iOS and Android water sort puzzle project.
The approved current scope includes the reusable portrait visual demo, general level core, seeded content tools, and a multi-bottle internal calibration trial. The core provides stable color/bottle IDs, shared explicit capacity, unified rules/sessions, bounded incremental solver, and JSON level encoding/decoding. The generator covers ordinary four-layer bottles, two to five colors, one or two empty bottles, full solution replay, basic filters, structural deduplication, and validated content-pool import/export. The visible app retains the original two-color four-bottle baseline and offers eight solver-validated calibration samples with two to five colors and four to seven bottles, tap-to-pour animation, free undo/reset, one-step hints, and phone/tablet adaptation. On 2026-10-07 the user approved the iPhone 12 Pro Max visuals and interactions, then reported that challenge samples felt too easy. The approved refinement applies diverse starts to D3 thinking and D4 challenge only: each initially filled bottle has at least three colors and no color exceeds two layers in total. D1 relaxed and D2 standard retain existing layouts. This is a generation/import filter, never a restriction on merging colors during play. C05, C07 and C08 were replaced with solver-validated candidates; C06 already met the filter and retains its layout. Preserve the accepted visuals and interactions. The user retested the diverse samples and found them acceptable with brief planning; C07 was identified as the hardest, with one spare for four colors. A four-layer planning evaluator specification now covers local consolidation, short-range choices, multi-stage coordination and global planning; it also records spare/color ratio and solvability with extra bottles. The approved offline planning evaluator is now implemented with bounded work/time, route evidence, deterministic report generation and recomputation. The app reads a bundled report for all eight samples plus the original demo and offers a per-level difficulty debug panel. Keep automated provisional ratings separate from editorial trial groups. No scoring weights, score bands, fifth tier or add-bottle behavior has been implemented. Read docs/difficulty-calibration.md before changing evaluation; limited search is unknown, never evidence of high difficulty or impossibility. D1–D4 remain provisional groups, not population-calibrated ratings or publication approval. The original visual baseline has also been approved on low-end Android; expanded content still needs Android testing and quantitative mobile solving/generation measurement. Measure TypeScript first and consider a C++ backend only if mobile results justify it. On 2026-10-07 the user approved completing the pure-play release path in order: content production, continuous play, local persistence, device/release verification, then store materials. The first 80-entry catalog contains 20 actually rated entries per D1–D4, solver/provenance validation and global structure deduplication. D3/D4 retain diverse starts. The app now provides first-use instructions, next-level progression, free skipping, fixed-tier play, a warm-up/mixed/relaxation sequence, and local progress/history restoration via AsyncStorage. Eight calibration samples remain separate. Finite content repeats explicitly after each tier pool is exhausted; mobile on-demand generation is not implemented. Read docs/play-flow.md before changing progression or persistence. Current new native storage and content require device checks; do not infer quantitative performance from desktop tests. Daily modes, special mechanisms, chapters, friends, accounts, lives, timers, payments and audio remain out of scope. Store submission awaits release verification and reviewed publishing identity/materials. Confirm any additional feature boundary before expanding game behavior.

On 2026-10-07 the user subsequently chose a fixed 1,000-level sequential mainline with replay of completed levels, cyclic recovery every ten levels, gradually growing bottle scale up to twelve bottles and eleven colors, and algorithmic refinement within the four player-facing tiers. They requested a concrete full-game production plan and an implemented objective model before producing the thousand actual levels. Read docs/production-plan.md for the current direction, exact quotas and implementation stages. The offline planning-depth-v1 / planning-load-v1 model now has eight internal grades, complete lower-policy evidence, fixed within-grade decision/operation load, and deterministic recomputation. The existing 89 layouts are re-rated offline; the phone still uses the 80-entry baseline and original report. productionPlan.ts is a recipe of 1,000 requested slots, not generated playable content. Twelve-bottle UI, eleven-color generation, actual thousand-level catalog, locked sequential progression, and formal/internal tool separation remain subsequent implementation stages. The previous statements about unimplemented weights apply to the original bundled report; the new production score is a fixed algorithmic ordering, not a population-calibrated rating. Preserve unknown results on any incomplete fine grading; never relabel candidates to fill target quotas. Keep daily modes and extra mechanics out of this mainline scope.

Work directly on main. Do not create feature branches or worktrees unless the user requests them. Keep this project independent from sibling projects.

The current thousand-waves-v3 recipe incorporates the user's corrections: every tenth-level closing challenge starts at internal grade 4 or higher and is selected by planning difficulty, with no stage-specific color band or color preference. Ordinary levels use overlapping soft preferred bands: 6–9 colors for levels 1–50, 7–10 for 51–250, 8–10 for 251–450, 8–11 for 451–700, and 9–11 for 701–1000. Only the first three teaching levels retain two to three colors. These preferences are not strict input boundaries; scale may rise, fall or repeat, independently of challenge scores. The overall twelve-bottle bound and diverse-start rules still apply. Layouts remain globally deduplicated. Exact current quotas are D1 300, D2 300, D3 305 and D4 95. Read production-plan.md and productionPlan.ts before changing this distribution.

## Development

Use Node.js 24 and npm. Keep package-lock.json current. Use Expo's compatible dependency versions and expo install for native libraries.

- npm start: Metro for the installed development build.
- npm run ios / npm run android: generate, build and launch a native development app.
- npm run typecheck: strict TypeScript checks.
- npm run lint: Expo ESLint checks.
- npx expo install --check / npx expo-doctor: dependency and configuration checks.

Native ios/ and android/ directories are generated from app.json with Expo Prebuild and are ignored by Git. Express native changes through app configuration or config plugins.

## Code and Tests

Use TypeScript, PascalCase for components and types, camelCase for functions, and use prefixes for hooks. Keep game rules and solver code independent from UI, animations and persistence.

Add meaningful tests when game behavior is implemented. Animation completion must not be the source of truth for liquid state. Do not generate or publish levels without solver validation.

## Stage

Pre-release development. Maintain one current internal baseline; do not introduce historical archives or migrations for unshipped experiments. Template icons and the initial application identifier must be reviewed before publishing.
